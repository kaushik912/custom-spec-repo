## Shorten URL — `POST /api/shorten`
Takes a URL, returns a short code and the full short URL (e.g. `<baseUrl>/<code>`).

| Scenario | Why it matters | Status |
|---|---|---|
| Happy path: valid `https://...` URL → 201, returns a short code + full short URL | baseline — nothing works if this breaks | not yet tested |
| Missing/null `url` field in the request body → currently crashes with an unhandled 500 (NullPointerException), instead of a clean 400 like other bad-input cases | looks like a real gap, not designed behavior — decide whether it should be 400, then test that | not yet tested |
| Malformed URL text (fails basic syntax, e.g. stray `%` or spaces) → 400 | standard validation | not yet tested |
| URL with no scheme (e.g. `example.com/path`) → 400 | standard validation | not yet tested |
| Non-http/https scheme (e.g. `ftp://...`, `javascript:...`) → 400 | standard validation, also blocks `javascript:` payloads | not yet tested |
| http/https scheme but no host (e.g. `http:///path`) → 400 | standard validation | not yet tested |
| Shortening the exact same URL twice → two different codes, both pointing at the same destination (no dedup) | undocumented design choice — is "always a new code" intended, or should repeats return the same code? | not yet tested |
| No max length enforced on the input URL — a huge URL (tens of thousands of chars) is accepted as-is | gap for a *shortening* service — decide if there should be a cap | not yet tested |
| Response shape: code is 6 alphanumeric chars, full URL is exactly `<baseUrl>/<code>` | catches a regression in the response-building logic itself | not yet tested |

## How to turn a scenario into a test
For any "not yet tested" row worth automating, hand it to the project's Bruno
regression-test workflow (see the `bruno` skill and the regression-testing
rule) — it already knows the `.bru` format and the plain-English `docs{}`
scenario block.
